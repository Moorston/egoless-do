## Context

首页数据卡目前包含饮水量和饮食记录两个模块。饮水量只有 +250ml 单按钮，饮食记录只显示总卡路里数字，添加食物需打开全屏 Modal。Web 端点击食物直接添加（无份量调整），Mobile 端有份量选择器。

当前交互路径：
- 喝水 500ml：点 2 次 +250
- 添加已知食物：打开 Modal → 搜索/浏览 → 点击 → 确认（3-4 步）
- 查看今天吃了什么：需打开 FoodLogPage

## Goals / Non-Goals

**Goals:**
- 饮水量支持多档快捷添加（200/250/350/500ml），1 步完成
- 饮食卡片内联今日记录列表，支持删除
- 最近常吃快捷入口，2 步完成添加（点击 → 份量确认）
- Web 端添加食物统一份量选择器

**Non-Goals:**
- 不新增 store 字段或数据模型
- 不修改 AddFoodModal 组件本身
- 不添加收藏/置顶食物功能

## Decisions

### 1. 饮水量按钮布局

**选择**：4 个等宽按钮一行排列（200/250/350/500ml）

**理由**：4 个数字覆盖常见杯量，一行排列不占过多空间。按钮风格使用 TH.card + TH.border + P 色文字，与统计卡片风格一致。

**替代方案**：
- 长按选量：增加操作步骤，违背"减少点击"目标
- 自定义杯量：增加设置复杂度，大多数用户不需要

### 2. 最近常吃数据来源

**选择**：从 `foodLog` 中按 `name` 聚合计数，取 top 3 非删除项

**理由**：无需新增 store 字段，foodLog 已有完整历史数据。`getTodayFoodLog()` 已有按日期过滤的工具函数，聚合并发可忽略。

**替代方案**：
- 新增 `recentFoods` store 字段：增加数据同步复杂度，与 foodLog 有冗余
- 手动收藏：需额外 UI 和操作，增加用户负担

### 3. 今日饮食列表展示

**选择**：默认显示最近 3 条，超过显示"共 N 条"提示

**理由**：3 条够覆盖一餐的典型数量，不会让卡片过长。超出部分用户可点击"共 N 条"展开或去 FoodLogPage 查看完整记录。

### 4. Web 端份量选择器

**选择**：复用 Mobile AddFoodModal 的份量选择模式（0.5/1/1.5/2x 按钮 + 卡路里计算 + 确认）

**理由**：保持 Web/Mobile 交互一致性。Web 端当前在 HomeTab 内联 food overlay 中直接 `addFood()`，改为先展示编辑区再确认。

**交互变更**：
- 单击食物 → 展开编辑区（份量选择）→ 确认
- 双击食物 → 快速添加 1 份（保留快捷通道）

### 5. 卡片标题

**选择**：饮食卡片标题从"添加饮食"改为"今日饮食"

**理由**：卡片已包含今日记录列表，"添加饮食"不再准确描述卡片功能。底部"添加饮食"按钮文案保留。

## Risks / Trade-offs

- **最近常吃准确性** → 从 foodLog 聚合可能受历史噪声影响（如一次性的聚餐）。接受此限制，top 3 已足够过滤偶发项。
- **卡片高度增加** → 内联列表使饮食卡片变高。通过限制 3 条 + 紧凑布局控制。
- **Web 双击检测** → 双击快速添加可能与单击有 300ms 冲突。使用 `onDoubleClick` 事件避免歧义。
