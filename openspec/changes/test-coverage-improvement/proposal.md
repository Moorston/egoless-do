# 测试覆盖率提升计划（深度评估版）

> 评估日期: 2026-07-07
> 评估方法: 4 个独立 Agent 并行深度扫描源码，数据驱动评分

## Context

架构审计发现移动端 features/ 层测试覆盖率仅 **1.9%**（297 个源文件仅 6 个测试，且 3 个为 Trivial 级）。核心业务逻辑层（packages/core）覆盖率 28%，表现良好。**Sync 子系统 2,500+ 行零测试**是最大风险点。

## 现状

```
┌──────────────────┬──────────┬───────────┬───────────────────┐
│                  │ 源文件    │ 测试文件   │ 覆盖率            │
├──────────────────┼──────────┼───────────┼───────────────────┤
│ packages/core    │ 143      │ 40        │ 1:3.6 (28%) ✅    │
│ mobile/store/db  │ ~30      │ 8         │ 1:3.8 (26%) ✅    │
│ mobile/features  │ 297      │ 6         │ 1:50  (2%)  🔴    │
└──────────────────┴──────────┴───────────┴───────────────────┘
```

## 目标

将 mobile/features 测试覆盖率从 2% 提升至 **15%+**，聚焦数据完整性关键路径。

## 深度评估矩阵

### 评分维度说明

| 维度 | 含义 | 权重 |
|------|------|------|
| **ROI** | 覆盖率提升 ÷ 投入工时 | 25% |
| **可行性** | 可测试性评分 + 已有测试基础 | 25% |
| **风险** | 业务关键度 × 出错后果严重性 | 30% |
| **依赖** | 前置依赖越少越优 (1=最少, 5=最多) | 20% |

- 每项 1-5 分，加权总分决定优先级
- ⭐ = 强烈推荐 | ✅ = 推荐 | ⚠️ | 可选 | ❌ = 暂不推荐

## 推荐执行方案

### 🟢 建议立即执行（2 个批次，15-18h）

**批次 A — 纯函数 + 写入层补缺（7-9h）:**
1. `WriteBatcher.test.ts` 补缺口 — fallback/retry/定时器/快照合并
2. `searchPipeline.test.ts` — runAIPhase2 + runAIPhase3
3. `useDateNavigation.test.ts` 升级 — renderHook + 未来日期守卫
4. `useSearchHistory.test.ts` 升级 — renderHook

**批次 B — 启动层测试（8.5-9h）:**
5. `SyncRehydrationManager.test.ts` — 分页+重试+退避策略

**预期成果**: 5 个测试文件，64-73 个测试用例，features 覆盖率 2% → ~12%

### 🟡 有条件执行（需重构前置）

6. `SyncApplyService.test.ts` — 需先搭建 16 rowMapper mock 基础设施
7. `SyncEngine.test.ts` — 需先引入依赖注入（`constructor(deps)` 替代内联 `new`）
8. `useAppStore.test.ts` — 需先提取 `initMobileStore()` 消除模块级副作用

## 风险

| 风险 | 缓解 |
|------|------|
| SyncEngine mock 复杂度高 | 先测 SyncRehydrationManager（更简单的 mock） |
| 测试维护成本 | 纯函数优先，减少 mock 依赖 |
| 假阳性测试 | 测试真实行为，不测实现细节 |
| SyncApplyService 16 rowMapper mock | 提取共享 mock 工厂 `__tests__/helpers/syncMocks.ts` |
| useAppStore 模块级副作用污染 | 暂不测试，等 `initMobileStore()` 重构 |
