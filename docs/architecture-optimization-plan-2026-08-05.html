一句话结论：地基是好的——单向依赖 app → core 守得住、核心层是唯一真源、计算下沉到端侧使服务端随用户增长的 CPU 成本近乎为零、可观测性（Sentry + PostHog）已接入。真正的问题不在"架构方向"，而在业务边界没闭合：引擎/服务仍泄漏到 apps/mobile 壳里、巨型文件在累积、质量门禁"半建成"（husky 调了 Prettier 却没装、覆盖率 provider 没接线、ESLint 还是 legacy）。本方案不推倒重来，而是把"该收口的地方收口"。

1.3 模块依赖分析

  • 守住 无 core → app 反向依赖：packages/core 内未出现任何指向 apps/mobile 的导入（红线条例 P3 合规）。
  • 守住 无 Zustand 全量订阅：扫描 useAppStore() 无参调用为 0，团队普遍使用选择器，重渲染风险低。
  • 残留 2 处跨 feature 导入：features/habits 与 features/settings 均 import ... from '../notifications/NotificationService'。即 notifications 是继 music 之后第二个"共享能力却挂在 features 下"的反模式。
  • 已修复 music 已于 2026-08-05 提升为共享层 apps/mobile/src/media/，9 处耦合归零。
  • 耦合枢纽（高扇入）：core/types、core/constants、core/store 切片、media/useMusicStore、features/sync 被最广泛引用——这些应是改动最谨慎的"稳定内核"。

1.6 业务痛点（从技术债翻译为人话）

  • 交付慢、易回归：引擎与业务逻辑散落在壳层，改一处要读懂 900+ 行文件；无强制覆盖率，核心纯逻辑（轨迹生成、反思图谱）改动无防护网。
  • 规模化天花板：单节点 PB 同时扛数据/实时/同步/限流，用户量或同步并发上来即单点抖动；没有缓存与队列吸收峰值。
  • 工具门禁形同虚设：husky 因 Prettier 缺失可能直接失败或静默跳过，宪法里的规范"写了没卡住"，新人容易又引入跨层耦合。
  • 重复踩同一个坑：共享能力反复被当 feature 放置（music→已修，notifications→在修），说明目录约定本身有缺口，需要结构性解法而非逐案修补。

1.7 架构优缺点汇总

优点（守住的）

  • 单向依赖铁律 app → core，无反向引用
  • Core 集中类型/常量/同步协议/i18n，真源单一
  • 计算下沉端侧，服务端随用户增长的 CPU 成本≈0
  • Zustand 选择器规范、音频单例、同步去抖——基础卫生好
  • 可观测性（Sentry+PostHog）已接入
  • husky/lint-staged/coverage 包已引入（在建）

缺点（待收口）

  • 引擎/服务泄漏到 apps/mobile 壳（违 P1/P2）
  • 巨型文件累积且变大，未收敛
  • 共享能力反模式复发（notifications）
  • 质量门禁半建成（Prettier 缺失/覆盖率未接线/ESLint legacy）
  • 单节点 PB 为规模化瓶颈
  • core 关键纯逻辑缺测试、测试文件自身膨胀

二、架构优化方案

2.1 模块拆分与边界界定

核心思路：建立"共享能力层"约定，让 media/notifications 这类"被多 feature 复用"的模块有合法归宿，从根上消除 §2.2 红线复发。同时把"引擎编排"从壳层抽回 core。

图 1 · 目标分层：薄壳 → 共享能力层 → core（引擎与共享能力各归其位）

ADR-01 · 设立"共享能力层"并提升 notifications

状态：建议采纳（Proposed） · 类型：模块边界

背景：features/habits 与 features/settings 跨 feature 引用 ../notifications/NotificationService，与已修复的 music 同构——证明"共享能力挂在 features 下"是结构性缺陷，逐案修会复发。

决策：在 apps/mobile/src/shared/ 下建立共享能力目录（与已落地的 src/media/ 并列）；将 features/notifications 整体迁至 src/shared/notifications/，保留其导航注册；更新 2 处消费者引用。

后果：§2.2 跨 feature 红线归零且不再复发；feature 目录仅含"真正独立业务域"。代价：需一次批量 import 改写（可脚本化，低风险）。

2.2 服务 / 组件职责重构

把 915 行的 SyncEngine 按职责拆为可独立测试的服务，并将编排逻辑下沉 core（符合 P1/P2）。音频/通知等能力已单例化，应复用既有模式。

图 2 · SyncEngine 职责拆分：巨型类 → 可测试服务组合

ADR-02 · 引擎编排下沉 core，壳层只做调度

状态：建议采纳（Proposed） · 类型：职责边界

背景：SyncEngine / BreathingEngine / SleepEngine 均在 apps/mobile，违反 P1（core=唯一真源）与 P2（app 是薄壳）。

决策：同步编排（ADR-01 拆出的服务）迁入 packages/core/src/sync/；Breathing/Sleep 的纯逻辑迁入 core/business/，RN 专属副作用（动画/计时器）留在 apps/mobile/src/features/*/engines 薄封装。壳层文件目标 ≤350 行。

后果：核心业务可跨端复用、可单测；壳层体积下降。代价：需界定"纯逻辑 vs RN 副作用"边界，分批迁移。

2.3 数据流与接口规范

当前数据通过 PB SDK + SSE 直连，缺少统一契约层。建议补三道规范：

规范落地方式收益
数据网关接口core 已有 DataGateway 抽象——强制所有端侧读写经此接口，禁止 feature 直连 PB SDK解耦、可 mock、可换后端
实体 DTO + zod 校验同步实体用 entitySchemas.ts（已 1228 行）统一校验；入站/出站 DTO 显式区分边界清晰、少运行时坑
领域事件总线core 内轻量 event-emitter（同步完成/冲突/网络变更），feature 订阅而非互相调用彻底消除 feature→feature 调用
错误信封统一 {code, message, retryable} 错误类型，UI 与重试策略据此分支容错策略一致
同步协议版本化sync payload 带 schemaVersion，后端按版本兼容演进客户端灰度、无断层升级

2.4 扩展性与容错能力提升

沿用蓝图结论：不要微服务化——计算已在端侧。真正的扩展点在"数据平面"与"故障吸收"。

图 3 · 数据平面解耦：网关无状态化 + PB 外置 + 对象存储 + 队列/熔断吸收故障
能力现状目标收益
限流/会话PB 内有状态Redis 外置，网关无状态可水平扩网关多实例扛峰值
主数据库PB+SQLite 单节点PB 接 Postgres（或外部 PG）读写分离、备份、垂直扩展
媒体随 PB 集合 / 本地对象存储 + CDN源站减负、端侧秒开
同步写直写 PB事件队列 + 幂等 + 退避削峰、防雪崩、可重放
故障隔离无熔断器 + 离线队列后端抖动不影响端侧使用
