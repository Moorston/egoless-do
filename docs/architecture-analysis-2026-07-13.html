三、当前仍存在的风险与技术债

#A 跨 feature 非法 import 反复出现 —— 根因是 music 被当共享模块用

首批 5 处已修复，但复扫又发现 9 处，且全部指向 features/music：

  • 组件级（4 处）：exercise/SportPage.tsx:24 → ../music/components/MusicPickerModal；meditation/MeditationScreen.tsx:22 → 同上；reflections/core/CreatePlanFromTrailModal.tsx:12 → ../../plan/components/PlanItemForm；reflections/core/CreatePlanFromReflectionModal.tsx:12 → 同上。
  • store/service 级（5 处）：zhiguan/ZhiguanScreen.tsx:15、exercise/SportPage.tsx:25-26、meditation/MeditationScreen.tsx:24、sync/useSync.ts:14 均 import useMusicStore / audioPlayerRef。

洞察：这不是偶发违规，而是结构性问题——music 本质是跨 feature 的共享媒体能力，却仍挂在 features/ 下。打地鼠式修 import 会无限复发。根本解法是把 music 提升为共享层（apps/mobile/src/components/media/ 或独立 packages/media），从根上消除这条红线。

四、改进建议（按性价比重新排序）

  1. 【治本】把 music 提升为共享层（解决 #A 反复复发）：新建 apps/mobile/src/components/media/（或独立 packages/media），迁移 MusicPickerModal、useMusicStore、audioPlayerRef、AudioSessionManager；再全局替换 9 处 import。一次改动即可永久消除这条 §2.2 红线，且能拦住未来复发。
  2. 补齐 4 个 core 测试缺口（#B）：precepts / sleep / zhiguanConstants / zhiguanMethods 写单测，兑现 P5。
  3. 收敛超大文件（#C）：优先拆 db/schema.ts(1203) 与两个 ~970 行文件；SyncEngine 按 AR-01 续推至 <600。
  4. 导航去耦合（#D）：将 useSync / isDeviceSyncedBefore 经路由表导出，移除 index.tsx 对 features 的直引。
  5. 拆分膨胀测试（#E）：rowMappers.test.ts 按实体拆分夹具。

五、结论

与一天前相比，项目的治理状态明显变好：宪法文档已校准到与代码一致，首批 5 处非法 import 已清除，3 个最高流量 core 纯逻辑文件已补测试。依赖骨架（app → core 单向）始终健康，PocketBase 唯一数据源自洽，auth 集合"缺失"实为设计而非缺陷。
