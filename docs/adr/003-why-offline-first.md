# ADR-003: 为什么离线优先

## 状态
已接受（2026-07-29）

## 背景
冥想/习惯追踪应用需要在网络不稳定或无网络时正常运行。

## 决策
采用 **离线优先（Offline-First）** 架构。

## 理由

| 因素 | 离线优先 | 在线优先 | 混合 |
|------|---------|---------|------|
| **用户体验** | 始终可用 ✅ | 网络差时不可用 | 部分可用 |
| **数据一致性** | 最终一致 | 强一致 | 最终一致 |
| **复杂度** | 高 | 低 | 中 |
| **冲突解决** | 需要 | 不需要 | 需要 |

**核心原则**:
1. **本地优先**：所有写操作先落 SQLite
2. **后台同步**：网络恢复时自动 push/pull
3. **冲突隔离**：单条失败不影响其他记录
4. **双层备份**：SQLite WAL + JSON 文件

## 架构设计

```
┌─────────────────────────────────────────────────────────┐
│  User Action → Slice Action → adapter.persistChange()   │
│                       ↓                                  │
│                  WriteBatcher (100ms)                    │
│                       ↓                                  │
│                  SQLite (WAL)                            │
│                       ↓                                  │
│                  sync_queue (pending)                    │
│                       ↓                                  │
│                  SyncEngine.runSync()                    │
│                       ↓                                  │
│                  PocketBase REST                         │
└─────────────────────────────────────────────────────────┘
```

## 后果

### 正面
- 无网络时完全可用
- 响应快（本地读写 <10ms）
- 流量节省（仅同步变更）

### 负面
- 冲突需手动解决（SyncConflictPanel）
- 存储占用较大（SQLite + JSON 备份）
- 初始化加载较慢（39 实体）

## 优化措施
- 关键/延迟实体拆分（已实施）
- 列表分页（已实施）
- FlashList 虚拟化（已实施）
