### P0-2：SyncEngine 并发守卫竞态

| 字段 | 值 |
|------|------|
| 类型 | 架构/Bug |
| 文件 | `SyncEngine.ts:487-498` + `:544-590` |
| 第1处：TOCTOU 竞态 | `if (this._syncing)` 检查和 `this._syncing = true` 之间，两个调用者可能同时通过 |
| 第2处：代际守卫不同步 | `_currentSyncGeneration` 与 `myGeneration` 在两个独立变量中，过期的 sync 可留下 `_syncing=true` 永久锁死 |

**影响**：并发 sync 导致数据损坏（push 时两批数据交叉写入），或完全锁死所有 future sync。

### P0-3：服务端 SQL 列名拼接（深度防御违规）

| 字段 | 值 |
|------|------|
| 来源 | 架构审查 C4 + 安全审查 H4 |
| 文件 | `SyncEngine.ts:275-304`、`SyncApplyService.ts:294-342` |
| 模式 | ``UPDATE ${config.table} SET ${setClause} WHERE ${config.pk}=?`` |

**影响**：`config.table` 和 `config.pk` 当前来自硬编码实体映射，但如果映射被破坏或从服务端 payload 动态派生，存在注入路径。`config.pk` 列名可用 `isValidSqlName()` 验证。

**修复**：所有表名/列名拼接经过 `isValidSqlName()` 验证。

### P0-4：Sentry 发送 PII（用户 email/姓名）

| 字段 | 值 |
|------|------|
| 来源 | 安全审查 H-1 |
| 文件 | `sentry.ts:49-66`、`initApp.ts:201-202` |

`setSentryUser` 将用户 `email` 和 `name` 附加到所有 Sentry 事件。`beforeSend` 只清面包屑数据中的 `token|password|secret`，不清用户上下文。

**修复**：`beforeSend` 中调用 `event.user = undefined`，或只在用户同意后才设置 email。

### P0-5：drainQueue 异步缺口导致 sync 项永久卡住

| 字段 | 值 |
|------|------|
| 来源 | Bug 审查 CRITICAL |
| 文件 | `SyncEngine.ts:217-371` |

`drainQueue` 原子标记为 `syncing`，`apiSyncPush` 调用失败后 `break` 退出循环，项留在 `syncing` 状态。`resetAllPendingForRetry` 有 LIMIT，超过批量的项永远不会恢复。

## 核心结论

**最强的系统性风险**在三个地方：

1. **SyncEngine 并发模型** — 当前用简单 boolean + generation 做并发控制，有多处竞态窗口。这是数据一致性的最大威胁。

2. **凭据泄漏到版本控制** — `.env` 文件包含完整的生产管理员凭证，应立即轮换并从 git 历史中清除。

3. **Sentry PII 泄漏** — 用户 email/姓名被明确发送到 Sentry，`beforeSend` 不清除。在没有 DPA 的情况下属于违规。

**值得肯定的设计决策**：
- `packages/core` 单向依赖 `apps/mobile`（包边界清晰）
- 同步引擎的 push-before-pull 分阶段设计思路正确
- 令牌存储用 `expo-secure-store`（iOS Keychain / Android EncryptedSharedPreferences）
- 坐标模糊化用加密种子随机化实现正确
