egoless-do · 大型系统架构蓝图与 3–5 年演进规划

面向业务规模持续增长与功能灵活扩展的整体架构方案 — 由软件架构师基于当前代码库实测状态起草

现状基准日 2026-08-05 PocketBase 0.38.2 / SQLite 单节点 客户端厚计算模型 模块化单体内核 + 抽取式服务
核心判断（先讲结论，避免架构太空步）。 你们的最大可扩展性优势是：几乎所有计算本来就在客户端——领域逻辑、RAG 检索、LLM 调用、本地 SQLite、通知排程、同步离线队列全部跑在设备上，用户增长几乎不增加服务器 CPU。因此本方案不主张"全面微服务化"，而是：保持客户端厚、解耦数据平面、仅对确实需服务端权威性的领域按触发点抽取服务。当前唯一的硬瓶颈是 单个 PocketBase+SQLite 节点，它同时承载数据写入、realtime SSE、同步写锁、以及（开启时）基于 PB 的限流——且没有任何缓存与消息队列作为减震层。架构演进的全部重心，就是把这块单点从"一切之母"降级为"可替换的存储协调者"。

一、现状真实体检（不是文件清单，是扩展天花板）

以下每一项均来自对仓库的只读核查，是后续所有决策的硬约束。

✅ 今天已能水平扩展的

  • 移动客户端：业务计算 100% 在设备侧，用户增长≈零服务器成本。这是系统最强的伸缩资产。
  • 静态音频：打包进 App 二进制，由应用商店 CDN 分发，无需服务端。
  • 推送扇出：Expo Push 代理 FCM/APNs，网关只负责每批 100 个 token 的聚合，压力外移。
  • nginx：本身无状态可复制（但当前 upstream auth-api 硬编码单后端，限流状态按实例翻倍）。

🔴 硬性单节点瓶颈

  • PocketBase + SQLite：单进程、单写者、宿主绑定挂载、container_name 写死、零复制。同时服务：全部同步写、每条 SSE 实时连接、auth 记录、push token、以及（开启时）每次限流的读+写。
  • Hono 网关不可复制：better-sqlite3 单进程、三处进程内存储（限流 / MFA 挑战 / 推送限流）。第二个实例会静默翻倍限流并作废进行中的 MFA 登录。
  • 无缓存、无队列：没有 Redis，没有消息代理，所有请求同步终止于 SQLite，唯一缓冲是每设备客户端发件箱。
  • 正确性天花板：冲突解决是整记录 LWW（基于客户端 updatedAt），无 CRDT / 版本向量；每用户设备数上升后静默字段丢失概率增加。
维度现状事实（实测）扩展影响
数据存储引擎PB 0.38.2 内置 SQLite；pb_data/data.db ≈ 2.6MB；无 Postgres/复制/litestream单写者天花板；写放大（/api/sync/push 在请求内串行 $app.save()）
缓存层无任何 Redis/Memcached；限流/MFA/推送均为进程内 Map；AI 缓存为设备端 LRU(50/5min)多实例即失效；重启丢 MFA 挑战
消息/事件总线无 Kafka/RabbitMQ/NATS/BullMQ；唯一"队列"是客户端 SQLite 发件箱（2000 容量）服务端无缓冲、无死信、无异步解耦
对象存储无 S3/MinIO/COS；pb_schema.json 中 file 类型字段数为 0；持咒/经文音频走"客户端下载未定义主机的 URL"远程音频无 CDN/源站；缺字段即降级 TTS

架构师提示：这些不是"技术债清单"，而是抽服务的优先级排序器。凡是"服务端需权威 + 写多 / 需异步 + 需管控"的领域，才值得抽取；纯客户端能力（RAG 检索、本地排程）应继续留在设备侧以省服务器成本。

二、架构原则（约束抽象，杜绝过度设计）

① 客户端保持厚

用户侧计算是零成本伸缩。任何"为了优雅"把客户端逻辑搬回服务端的提议，默认否决。

② 数据平面先解耦

单点 PB 是第一风险。先于任何功能扩张，先把同步写、缓存、媒体从单节点卸载。

③ 按触发点抽服务

不预设微服务。只有当某领域越过"写吞吐 / 异步需求 / 管控需求"阈值，才抽取，且保留回退路径。

④ 可逆优先

优先选易回退的决策（特性开关、事件日志可重放、按服务分库）而非"最优但锁定"的方案。

⑤ 文档决策非设计

每条关键决策写 ADR，记录"放弃了什么"，而非只记"做了什么"。

⑥ 模块化边界即反腐层

服务间、客户端与 PB 间全部经明确定义的接口（核心已有的 §2.1 决策树升级为正式契约）。

三、分层架构（C4 视角：当前 → 目标）

当前（C0）：客户端厚 + 单点服务端

目标（C3，3 年内）：客户端厚 + 网关无状态 + 抽取式领域服务 + 解耦数据平面

四、核心模块 / 限界上下文划分

以领域驱动划分限界上下文（Bounded Context）。关键原则：上下文内部自治，上下文之间只经"反腐层（ACL）"通信；客户端与 PB 之间的同步协议本身就是第一道反腐层。

五、服务间通信机制

通信对机制选型理由 / 取舍
客户端 ↔ 网关REST + SSE（实时）；未来可选 BFF GraphQL 聚合沿用既有；放弃：早期上 GraphQL 增加客户端复杂度，待多端聚合需求明显再加
网关 ↔ 领域服务内部 REST（同步短事务）/ gRPC（高吞吐内部调用）REST 简单可逆；gRPC 仅在 Sync/AI 高吞吐链路引入
服务 ↔ 服务（异步）消息总线（NATS 优先，Kafka 为大规模备选）NATS 轻量、运维成本低、易回退；放弃：Kafka 早期过重。换来：事件溯源、削峰、重放能力
同步写路径客户端发件箱 → Sync 服务 → 追加式事件日志（不在请求内串行 save）放弃：请求内整批串行写入的吞吐与锁竞争；换来：写可水平扩展、断点重放、冲突可审计
读路径CQRS：写主库 + 读副本/物化视图（洞察、关系图）读多写少场景收益大；放弃：强一致实时读（修行数据最终一致可接受）
客户端实时经网关代理的 SSE（不再直连 PB）；或 WebSocket 网关修正当前"绕过网关直连 8090"的架构违例；统一入口、统一鉴权

六、数据存储策略（按域分治，读写分离）

持久化（OLTP）

  • 主库 Postgres：高写领域（同步日志、分析、通知、AI 作业）各自库或共享按服务分库。
  • PocketBase 退居：保留为认证 + 同步协调者；若 PB 后续支持外部 DB 则切换后端，否则将其"协调者"职责（冲突仲裁、token 发牌）保留、数据落库外移。
  • 客户端 SQLite：离线真源，冲突在拉取/推送时由 Sync 服务仲裁。

缓存 / 高速 / 特殊存储

  • Redis：网关限流、MFA 挑战、会话、AI 结果缓存、热点读模型。
  • 对象存储 + CDN：持咒/经文/用户音频，替代"未定义主机的远程下载"。
  • 向量库（pgvector 或 Qdrant）：AI 网关服务端 RAG 检索。
  • 搜索（Meilisearch/OpenSearch）：内容库规模化后的检索。
关于 PocketBase 0.38 的硬约束：当前版本仅支持 SQLite，无外部 DB 开关。因此"把 PB 换成 Postgres"不是一行配置，而是架构动作。两条可逆路径：
(A) 最小风险：保留 PB 作协调者，把高写领域（同步事件日志、分析、AI 作业）抽到独立 Postgres 服务，PB 仅存"协调元数据"——客户端离线模型不变。
(B) 等待/升级：待 PB 原生支持外部 DB 后再迁移数据平面。本蓝图默认采用 (A)，因为它不锁定、可逐步推进，且立即解除单点写瓶颈。

7.1 水平扩展（Horizontal Scaling）

组件扩展方式当前障碍 → 目标

7.2 插件化 / 功能灵活扩展（Plugin Model）

这是"功能模块灵活扩展"的核心答案，且不增加服务端负担——因为新增修行类型本就主要发生在客户端。

  • 修行类型数据驱动化：将"持咒/禅修/运动/素食/止语"从硬编码 feature 变为数据驱动的插件描述（元数据：名称、图标、计分规则、是否需音频、是否需计时）。新增一种修行 = 配置 + 一个小 feature 模块，不改 core。
  • Feature Registry：客户端启动时从核心注册表加载可用修行模块；core 只定义插件契约（接口），不感知具体实现。
  • 共享媒体层提升：把反复被 5 个模块直引的 features/music 提升为 components/media/（或独立 packages/media），以共享层契约消除 §2.2 红线复发——这本身即"插件底座"。
  • 服务端插件点：AI 网关以"provider 插件"接入不同 LLM；通知服务以"通道插件"接入 Expo/短信/未来自有通道。

7.3 微服务 / 模块化边界（何时抽、何时不抽）

保持模块化单体（暂不抽）

  • packages/core 领域模型：仍是单一可信源，按 bounded context 分包即可。
  • 洞察/分析：经读副本满足，不必独立服务。
  • 客户端各 feature：经 Feature Registry 自治。

越过阈值即抽取（带触发点）

  • Sync 服务：单 PB 写入延迟/P99 越线，或日同步事件 > N 百万。
  • AI 网关：出现成本失控/合规/密钥泄露风险（基本必然，建议 M1 即抽）。
  • 通知服务：需服务端触达/留存营销/跨设备可靠提醒。
  • 内容/媒体服务：远程音频/内容规模上升。

八、3–5 年技术演进路线（触发点驱动，非时间表驱动）

阶段 0 · 稳定与解耦（0–3 个月）— 快赢
  • 清理配置漂移：删除死 Dockerfile.web；统一两份 compose；将 nginx.conf 纳入 compose 托管。
  • 网关无状态化：引入 Redis 承载限流/MFA/推送状态，使 Hono 可多实例。
  • 修复架构违例：将 features/music 提升为共享媒体层，清零 9 处跨 feature 非法 import（一次性根治 §2.2 红线）。
  • 媒体外置：对象存储 + CDN 接管远程音频，消除"无源站下载"。
  • 建立同步事件日志原型（落 Postgres），替代请求内串行 save——这是解除单点写的第一刀。
阶段 1 · 首个服务端抽取（3–12 个月）
  • AI 网关 + 服务端 RAG：密钥库外置、成本帽、调用审计、向量检索；用户 Key 不再穿越同步管线。
  • 通知服务 + 服务端调度：可靠触达、留存能力、跨设备提醒。
  • 读写分离：洞察/分析走读副本 + 物化视图（CQRS 读模型）。
  • 客户端 Feature Registry + 修行类型数据驱动化（插件化落地）。
  • 可观测性基线：集中日志、追踪（跨边界 traceId）、核心 SLI。
阶段 2 · 数据平面成熟（1–2.5 年）
  • 事件总线常态化（NATS→Kafka 按规模）：同步、推送、分析摄取、AI 作业全异步解耦。
  • PocketBase 退居"认证+协调者"，高写域全面落到独立 Postgres（路径 A 完成）。
  • 冲突解决升级：引入版本向量 / 字段级 CRDT，消除多设备静默丢失。
  • 媒体管线完备：转码、多码率、全球 CDN。
  • 多区域只读副本（若用户跨地域增长）。
阶段 3 · 平台化（2.5–5 年）
  • database-per-service 成熟，团队按限界上下文独立交付（康威对齐）。
  • 特性开关 + A/B 实验平台；AI 个性化推荐服务。
  • 若需，重引 Web/Desktop 薄壳——复用已可移植的 packages/core。
  • 高级 DORA 度量、混沌演练、SLO 文化。
  • 合规与多租户（如出海/机构版）作为独立强隔离上下文。

九、关键架构决策记录（ADR，节选）

ADR-EXT-001 · 引入服务端同步事件日志，替代请求内串行写入

状态：Proposed · 提出 2026-08-05

Context：/api/sync/push 在 HTTP 请求内对整批变更串行 $app.save()，持有 SQLite 写锁整段时长；单 PB 节点成为唯一写入瓶颈，且大批量请求会拖垮实时连接。

Decision：客户端发件箱写入 Sync 服务后，变更以追加式事件日志（Postgres）持久化，由消费者异步落库；支持断点重放与冲突审计。PB 退居协调者。

Consequences：✅ 写路径水平扩展、削峰、可重放、冲突可查。❌ 引入异步一致性与新组件运维成本；需定义事件 schema 版本化。

ADR-EXT-002 · AI 能力由客户端迁移至服务端 AI 网关

状态：Proposed · 提出 2026-08-05

Context：AI 100% 客户端运行，用户 API Key 作为同步实体穿越同步管线；无成本管控、密钥轮换、调用审计、滥用防护的服务端控制点；检索为关键词打分而非向量。

Decision：建立 AI 网关：密钥库外置、成本帽、审计日志、provider 插件化，并以向量库承载服务端 RAG。客户端通过网关调用，本地保留离线降级路径。

Consequences：✅ 成本可控、合规可达、检索质量提升、密钥不随同步流动。❌ 新增服务端 AI 负载与延迟；需保留客户端降级以防网关不可用。

ADR-EXT-003 · 修行类型数据驱动插件化

状态：Proposed · 提出 2026-08-05

Context：新增一种修行（如"抄经""诵经"）当前需改 core + 新建 feature，违反"灵活扩展"诉求，且 music 被 5 模块直引暴露耦合。

Decision：修行类型改为数据驱动的插件描述 + 客户端 Feature Registry；features/music 提升为共享媒体层契约。core 只定义插件接口。

Consequences：✅ 新增修行≈配置+小模块，不改 core；从根消除 §2.2 红线复发。❌ 需设计插件契约与版本兼容策略，初期有迁移成本。
